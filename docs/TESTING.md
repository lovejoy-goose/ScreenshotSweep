# Проверки и тестирование

## Окружение

- Локально может не быть Xcode (только Command Line Tools). Тогда сборка проверяется в CI.
- CI: `.github/workflows/build-ios.yml` на `macos-15` — `xcodegen generate` → `xcodebuild -scheme KatanaConnector` (unsigned, `iphoneos`) → `KatanaConnector.ipa` в артефакте `katana-connector-unsigned-ipa`. Запускается на push в `main`, на PR и вручную: `gh workflow run build-ios.yml --ref <ветка>`.
- Установка на устройство — Sideloadly (см. `README.md`).
- Unit-тесты: target `KatanaConnectorTests` (XCTest) компилирует `Sources/Core` без host app (D-018). В CI шаг «Unit tests (iOS Simulator)» выполняется до device-сборки на динамически выбранном iPhone Simulator.
- Локальный запуск требует Xcode: `xcodegen generate`, затем `xcodebuild -project KatanaConnector.xcodeproj -scheme KatanaConnector -destination 'platform=iOS Simulator,name=<доступный iPhone>' CODE_SIGNING_ALLOWED=NO test`.

## Обязательные проверки после каждой задачи

| Проверка | Команда / способ | Когда |
|---|---|---|
| YAML валиден | `ruby -ryaml -e 'YAML.load_file("project.yml"); YAML.load_file(".github/workflows/build-ios.yml")'` | всегда |
| XcodeGen читает проект | `xcodegen dump --type summary` или `xcodegen generate` | если установлен XcodeGen |
| Сборка | `xcodebuild … build` как в CI | если есть Xcode; иначе — CI после push (с разрешения пользователя) |
| Unit-тесты | `xcodebuild … test` (см. выше) или шаг CI | всегда при изменении Swift |
| Diff | `git diff --stat`, `git status` — нет лишних файлов, секретов, `*.xcodeproj` | всегда |
| Приватность | поиск `print(`, `os_log`, `Logger` в изменённых файлах — нет `localIdentifier`, токенов, payload | всегда при изменении Swift |
| Старые имена | `rg "ScreenshotSweep\|local\.sweep" .` — только исторические упоминания в документации и имя GitHub-репозитория | после переименований |
| Ручная регрессия | чек-листы ниже | при изменении Swift-кода |

## Pairing: что покрыто unit-тестами

Парсер QR (валидный QR, схема/хост/версия, код, `base_url`, HTTP, credentials/query/fragment), точный JSON запроса, декодирование ответа, маппинг ошибок (410/4xx/5xx/3xx/404/timeout/размер), отсутствие секретов в `description`/`debugDescription`/`dump`, координатор с in-memory store (токен сохраняется ровно один раз, при ошибке не сохраняется, локальное отключение удаляет, отсутствующий/нечитаемый Keychain → unpaired). Реальный Keychain в CI не используется.

## Event delivery: что покрыто unit-тестами (KC-005)

- **EventQueue** (временный каталог): переживает новый экземпляр, FIFO, дедупликация `event_id` с исходным payload, batch ≤ 20, accepted/duplicate удаляются, rejected → журнал без payload (с лимитом), повреждённый файл переносится в quarantine с исходными байтами, исключение из backup и file protection (если симулятор сообщает), лимиты очереди/события/типа, точный wire format события.
- **API client** (mock URLProtocol, in-memory credentials): точные пути/методы/заголовки, Bearer отправляется, но не попадает в описания, редиректы не выполняются, check/capability report/event batch, строгая проверка `event_id`, ответ > 64 KiB, классификация 401/408/429/4xx/5xx/timeout, без credentials/с `requires_repair`/HTTP/ошибкой Keychain запрос не отправляется, snake_case capability JSON.
- **Delivery coordinator** (mock API, recording sleeper): один flush одновременно, backoff 2/4/8 с через injectable sleeper, retryable-ошибки и timeout сохраняют очередь, отмена сохраняет события, 401 → requiresRepair без повторов и без потери очереди (и флаг в Keychain), 4xx batch не удаляет события, capability report один раз за запуск, результаты check connection, повреждённая очередь видна UI, нет токена и payload в описаниях.

## Connection scope и Screenshot Cleanup: что покрыто unit-тестами (KC-006)

- **ConnectionScopeTests:** каноническая форма `base_url`; событие получает scope текущего подключения, без подключения не создаётся; flush отправляет только текущий scope; другой `device_id` и другой `base_url` не получают старые события; клиент отказывает при `scopeMismatch` без сети; повторное pairing к тому же scope (новый токен) отправляет очередь; legacy-события не назначаются подключению; миграция v1 → v2 сохраняет события, журнал rejected и исходные байты; в scope нет токена, его SHA-256 и base64.
- **CleanupSessionTests:** round-trip и точный wire format summary и события; инварианты; трекер учитывает удаление даже если медиатека сообщила изменение раньше завершения запроса, отмена системного диалога оставляет «отмечено»; завершение даёт ровно одно событие; превью и повторное открытие не создают дубликатов; отмена не создаёт событие; offline оставляет событие в persistent queue; ошибка очереди → `failed` без влияния на состояние удаления; payload без идентификаторов снимков, только 7 ключей; успешный flush удаляет событие текущего scope, чужое не трогает; без подключения ничего не записывается.

## Custom URL scheme: что покрыто unit-тестами (KC-007)

- **ConnectorURLRouterTests:** валидные ссылки screenshot_cleanup и pairing; точные wire values и построение ссылок; неверные scheme/host/версия, отсутствующие `v`/`feature`, неизвестный feature; повторяющиеся и неизвестные параметры, пустые значения; user/password, port, fragment, лишний path; длина > 2048 и непечатные символы; token/code/base_url/device_id отклоняются; pairing QR не принимается роутером (но принимается QR-парсером); `Config/KatanaConnector-Info.plist` регистрирует схему.
- **AppNavigatorTests:** холодный старт открывает нужный экран; тёплый старт детерминированно заменяет стек; повтор ссылки не дублирует экран; невалидная ссылка не меняет навигацию; ссылка не трогает pairing, сеть, flush, события и состояние удаления.
- **CI:** шаг упаковки проверяет, что в собранном `KatanaConnector.app/Info.plist` зарегистрирована схема `katana-connector`.

## Capability Lab: что покрыто unit-тестами (KC-008)

`CapabilityLabTests` — только mock-адаптеры, без hardware и реальных запросов:
- общие: probe меняет только свой snapshot; probes независимы, отказ не распространяется; один запуск одновременно и один системный запрос при повторных тапах; таймаут → `failed`/`timed_out` и остановка обновлений; отмена → `failed`/`cancelled`, сессия остановлена, повторный запуск работает; сохранение и восстановление; битое/неизвестной версии/с неизвестным ID хранилище — quarantine без падения; реестр полный и в порядке; capability report содержит обновлённые snapshots только с разрешёнными полями и кодами, без событий; ошибка сети сохраняет результат; foreground refresh не запрашивает и не запускает probes и не подделывает `probe_state`/`checked_at`;
- камера: запрос → один кадр → `passed`; denied/restricted — без захвата; кадр нигде не появляется; нет камеры → `unsupported_device`;
- геолокация: только When In Use, одна фиксация, обновления остановлены; denied/restricted — без обновлений; координаты нигде не появляются; в `Sources` нет вызовов Always/фоновых обновлений/геозон;
- движение: одно событие, обновления остановлены; denied/restricted — без обновлений; данные движения нигде не появляются; неподдерживаемое устройство честно отражается;
- уведомления: запрос ровно один раз; одно тестовое уведомление; denied — ничего не планируется; provisional/ephemeral → `limited`; нейтральный текст и идентификатор; ошибка планирования → `system_error` без сырого текста;
- wire и конфигурация: точные коды `detail`, mapping статусов, round-trip файла, Info.plist-ключи When In Use/Motion/Camera, отсутствие Always/background modes/entitlements, сохранённая URL-схема, Core без hardware-фреймворков.
- **CI:** шаг упаковки проверяет наличие `NSCameraUsageDescription`, `NSLocationWhenInUseUsageDescription`, `NSMotionUsageDescription`, `NSPhotoLibraryUsageDescription` и отсутствие `NSLocationAlways*`, `UIBackgroundModes` в собранном Info.plist.

## Ручной чек-лист Capability Lab (на устройстве)

Перед проверкой: удалить и заново установить IPA (чтобы все разрешения были «не запрашивались»), Katana подключена.

1. Запуск → Dashboard: ни одного системного запроса; «Возможности устройства»: Камера, Текущая геолокация, Движение, Локальные уведомления — `untested`; Фоновая геолокация — `planned`; HealthKit — `missing entitlement`.
2. Dashboard → «Capability Lab» → четыре карточки; системных запросов нет.
3. «Проверить камеру» → только запрос камеры → «Разрешить» → через секунду «Результат: работает», «Камера передала кадр; кадр отброшен». Превью нет; в «Фото» ничего не появилось; индикатор камеры гаснет.
4. «Проверить геолокацию» → запрос геолокации с вариантами «При использовании»/«Один раз»/«Не разрешать» (без «Всегда») → «Разрешить при использовании» → «работает», координат на экране нет.
5. «Проверить датчики движения» → запрос «Движение и фитнес» → «Разрешить» → «работает» (если устройство не поддерживает — «не поддерживается устройством»).
6. «Отправить тестовое уведомление» → запрос уведомлений → «Разрешить» → «работает», «Тестовое уведомление запланировано». Свернуть приложение — через ~5 с баннер «Katana Connector / Тестовое уведомление Capability Lab.».
7. Повторить одну из проверок, во время прогресса быстро нажать кнопку ещё раз нельзя (показан прогресс) — второго системного запроса нет; «Отменить» → «Проверка отменена».
8. Отказ: в Настройках запретить камеру → вернуться (проверки сами не запускаются; «Разрешение: запрещено», прежний результат и время не изменились) → «Проверить камеру» → «Доступ запрещён…» и кнопка «Открыть Настройки»; другие карточки не изменились.
9. Dashboard показывает те же состояния, что карточки.
10. В Katana (Settings → Devices) у устройства обновились camera / current_location / motion / local_notifications: только состояния и коды, без координат, кадров, данных движения и текста ошибок.
11. Авиарежим → выполнить probe → результат на iPhone есть; выключить авиарежим, вернуться в приложение → отчёт уходит.
12. Перезапуск приложения → результаты сохранились.

## Ручной чек-лист custom URL scheme (на устройстве)

Ссылки можно открыть из Safari/Заметок или кнопкой/QR в Katana.

1. Приложение закрыто полностью → `katana-connector://open?v=1&feature=screenshot_cleanup` → Connector запускается сразу на экране «Скриншоты».
2. При первом использовании: экран «Доступ к скриншотам», системного запроса нет, пока не нажата «Разрешить доступ к фото».
3. Приложение в фоне на Dashboard → `…feature=pairing` → открывается экран «Подключить Katana»; камера не запрашивается, подключение не создаётся (если уже подключено — показывается «Katana подключена»).
4. На экране «Скриншоты» снова открыть ссылку screenshot_cleanup → экран не дублируется, прогресс разбора сохранён.
5. С открытым экраном проверки (sheet) открыть ссылку pairing → sheet закрыт, открыт экран подключения; ничего не удалено.
6. Невалидные ссылки (`…v=2…`, `…feature=unknown`, `…&token=x`, `katana-connector://pair?...`) → приложение открывается, текущий экран не меняется.
7. Ни одна ссылка не удаляет скриншоты и не отправляет событие сама по себе.

## Ручной чек-лист Screenshot Cleanup → Katana (на устройстве)

1. Katana подключена. Открыть «Разобрать скриншоты», принять 3–5 решений (оставить/на удаление), один раз «Отменить».
2. Внизу появилась кнопка «Завершить разбор» → экран итога: числа совпадают с решениями, текст про то, что уходят только числа и время.
3. «Продолжить разбор» → возврат к разбору; на сервере ничего не появилось.
4. Удалить кандидатов через экран проверки (оба подтверждения) → «Завершить разбор» → «Завершить» → «Результат сохранён для Katana» → через несколько секунд «Результат отправлен в Katana».
5. На сервере Katana одно событие `screenshot_cleanup.completed` с теми же числами и `deletion_completed: true`; никаких данных о снимках.
6. Повторно открыть «Завершить разбор» → новый пустой итог/кнопка неактивна; второго события нет.
7. Авиарежим → новый разбор → «Завершить» → «Результат сохранён для Katana…»; Dashboard «Событий в очереди: 1»; выключить авиарежим, вернуться в приложение/«Синхронизировать» → 0, событие на сервере.
8. Отменить системный диалог удаления → «Завершить» → `deletion_completed: false`.
9. Скриншоты удаляются только как раньше; «Недавно удалённые» содержит их.

## Ручной чек-лист синхронизации (на устройстве, с реальным Katana API)

1. После pairing Dashboard показывает раздел «Синхронизация»: «Последняя синхронизация», «Событий в очереди: 0».
2. Запуск/возврат в foreground → capability report уходит автоматически (на сервере видно), «Последняя синхронизация» обновляется.
3. «Проверить соединение» → «Соединение в порядке · <account_label>».
4. «Синхронизировать» без событий → без ошибок.
5. Авиарежим → «Проверить соединение» → «Нет соединения с Katana»; токен и сырые ошибки нигде не показываются.
6. Отозвать устройство в Katana → «Проверить соединение» или «Синхронизировать» → «Требуется повторное подключение», кнопки синхронизации неактивны; после перезапуска состояние сохраняется и запросы не уходят.
7. «Подключить Katana заново» → подтверждение показывает предупреждение о замене → после подключения статус «Katana подключена», синхронизация снова работает.
8. Если в очереди есть события другого или прежнего подключения — строка «Ждут решения (другое подключение)»; «Синхронизировать» их не отправляет.

## Ручной чек-лист Pairing (на устройстве)

1. Свежая установка → Dashboard: «Katana не подключена», кнопка «Подключить Katana»; камера **не** запрашивается.
2. «Подключить Katana» → экран объяснения; камера всё ещё не запрошена.
3. «Сканировать QR» → только теперь системный запрос камеры. Отказ → экран «Нет доступа к камере» с переходом в Настройки.
4. Сканирование произвольного QR → «Не удалось подключиться» с понятным текстом; сеть не используется.
5. QR с `http://` → отказ «не использует HTTPS».
6. Корректный QR → камера гаснет; показан хост, поле имени (`iPhone`), предупреждение, «Подключить»/«Отмена».
7. «Отмена» → назад к объяснению, код не отправлен.
8. Без доступного endpoint → «Нет соединения с Katana» / «Katana ответила неожиданно»; Dashboard остаётся «не подключена».
9. С реальным endpoint (KC-004 e2e): «Подключить» → «Katana подключена» → Dashboard показывает хост, имя, время подключения.
10. Перезапуск приложения → состояние connected сохраняется.
11. «Отключить на этом iPhone» → подтверждение с честным текстом про сервер → «не подключена»; перезапуск подтверждает.
12. Переустановка через Sideloadly с другим Apple ID → «Сохранённое подключение недоступно…» или просто «не подключена», без падения.

## Ручной регрессионный чек-лист Screenshot Cleanup

Выполняется на устройстве с тестовыми скриншотами (сделать 5–10 «мусорных» скриншотов заранее).

1. Свежая установка → Dashboard → «Разобрать скриншоты» → экран «Доступ к скриншотам» → «Разрешить доступ к фото» → только теперь iOS запрашивает доступ.
2. «Все фото» → видны скриншоты от старых к новым, счётчик «Обработано: 0 из N».
3. «Выбранные фото» → жёлтый баннер ограниченного доступа, «Выбрать ещё» открывает системный picker.
4. Отказ → экран «Нет доступа к фото» с кнопкой в Настройки.
5. Свайп вправо / «Оставить» — следующий скриншот, счётчик +1.
6. Свайп влево / «На удаление» — счётчик кандидатов +1.
7. «Отменить» несколько раз подряд — возвращает предыдущие скриншоты, решения откатываются.
8. После 30 решений (при наличии кандидатов) открывается экран проверки.
9. На экране проверки тап по скриншоту убирает его из кандидатов.
10. «Удалить N шт.» → диалог приложения → «Отмена»: ничего не удалено.
11. «Удалить» → системный диалог → «Не разрешать»: ничего не удалено, ошибки не показано.
12. «Удалить» → системный диалог → «Удалить»: сообщение «Удалено: N…», скриншоты в «Недавно удалённых».
13. Изменить медиатеку извне (сделать новый скриншот) во время разбора — порядок уже решённых не ломается.
14. Ни на одном шаге медиатека не меняется без двух подтверждений.
15. «Главная» возвращает на Dashboard; повторный вход сохраняет прогресс и кандидатов (до перезапуска приложения); повторного запроса разрешения нет.

## Проверки будущих задач (кратко)

- **KC-004:** токен только в Keychain; повторный запуск сохраняет pairing; revoke удаляет токен; невалидный/просроченный QR — понятная ошибка.
- **KC-005:** событие переживает kill приложения и офлайн; повторная отправка того же `event_id` не создаёт дубль (сервер или mock отвечает `duplicate`); 401 не теряет очередь.
- **KC-007:** некорректные/длинные/неизвестные URL игнорируются безопасно; URL не может вызвать удаление.
- **KC-008:** каждый probe запрашивает только своё разрешение и только по нажатию.
- **KC-009:** сквозной сценарий PWA → Connector → API на тестовом (не production) окружении.

Тестовые серверы, токены и URL — только плейсхолдеры или локальные mock; production credentials в репозитории запрещены.
