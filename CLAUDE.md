# CLAUDE.md — правила работы в репозитории

Приложение: **Katana Connector** (`app.katana.connector`, target `KatanaConnector`), исходно — ScreenshotSweep. Рабочая ветка v0.1: `feature/katana-connector-v0.1`, одна KC-задача = один коммит.
Продукт и архитектура описаны в `docs/`. Этот файл — постоянные правила, которые действуют в каждой сессии.

## Перед изменениями

1. Прочитать `docs/TASKS.md` и найти текущую задачу (статус `in progress`) или следующую `planned`, которую явно назвал пользователь.
2. Прочитать документы, связанные с задачей (указаны в поле «Документы» задачи), минимум:
   `docs/PRODUCT.md`, `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`; для сети — `docs/API.md`; для проверок — `docs/TESTING.md`.
3. Если задача противоречит `docs/DECISIONS.md` — остановиться и спросить, а не менять решение молча.

## Объём работы

- Брать **ровно одну** задачу из `docs/TASKS.md`.
- **Не переходить** к следующей задаче самостоятельно, даже если текущая закончена раньше.
- Не расширять scope задачи. Найденное «по пути» записать в отчёт или в `docs/TASKS.md` как заметку, но не делать.
- Не коммитить и не пушить без явного разрешения пользователя.
- Не добавлять сторонние зависимости (SPM/CocoaPods/Carthage) без отдельного решения в `docs/DECISIONS.md`.

## Безопасность и приватность

- Никаких секретов, реальных токенов, production URL и production credentials в коде, конфигурации, тестах, документации и истории git. Только явные плейсхолдеры (`<API_BASE_URL>`, `example.invalid`).
- Device token хранится только в Keychain (`KeychainTokenStore`) и читается API-клиентом только перед запросом. Не в `UserDefaults`, не в файлах (включая очередь событий), не в логах, не в `@Published`, не в UI, не в query. Секреты передаются только в обёртках `DeviceToken`/`PairingCode` с редактированным описанием; описания событий не содержат payload.
- Очередь событий не удаляется ни при 401, ни при отключении, ни при повторном pairing без отдельного подтверждения пользователя. События отправляются только подключению, для которого записаны (connection scope, D-029); legacy и чужие scope автоматически не отправляются.
- Cleanup-событие содержит только агрегаты (D-031); идентификаторы снимков не покидают память `CleanupSessionTracker`.
- Не логировать содержимое фотографий, `PHAsset.localIdentifier`, имена файлов, даты отдельных снимков, EXIF/геоданные, токены, pairing-коды, тела запросов с чувствительными данными. Допустимы только агрегаты (счётчики) и коды ошибок.
- Фотографии и их производные (превью, хэши, метаданные) **никогда** не отправляются в Katana. Сервер получает только итоги cleanup-сессии (см. `docs/API.md`).
- Всё, что приходит через custom URL scheme, QR-код или ответ сервера, — недоверенный ввод: валидировать, не выполнять разрушительных действий без подтверждения в UI.

## Разрешения

- Системные разрешения запрашиваются **только после явного действия пользователя** (нажатие кнопки, относящейся к функции), по одному, в момент, когда функция реально нужна.
- Никогда не запрашивать несколько разрешений сразу и не запрашивать их на старте приложения.
- Каждое новое разрешение = новый `INFOPLIST_KEY_*Usage Description` в `project.yml` + запись в `docs/DECISIONS.md`.
- Dashboard не запрашивает разрешений. Доступ к фото — только кнопкой «Разрешить доступ к фото» внутри Screenshot Cleanup (D-033); камера — только «Сканировать QR».
- Custom URL scheme (D-032) только открывает экран: никаких удалений, pairing, сети, flush, credentials и запросов разрешений по ссылке.
- Capability Lab (D-034, D-035): каждый probe — только своей кнопкой и только своё разрешение; геолокация только When In Use (Always-ключей и API нет); кадры, координаты и данные движения не покидают адаптеры (Void-API); в snapshot — только безопасные коды `CapabilityProbeDetail`.

## Безопасная модель удаления (PhotoKit)

Не ослаблять ни при каком рефакторинге:

- Медиатека изменяется только в одном месте — `deleteCandidates()` (или его прямом преемнике).
- Удаление происходит только после: решения пользователя → экрана проверки → подтверждения в приложении → системного диалога iOS.
- Одна транзакция `PHPhotoLibrary.performChanges` с `PHAssetChangeRequest.deleteAssets`; файлы уходят в «Недавно удалённые».
- Отмена в системном диалоге (`PHPhotosError.userCancelled`) — не ошибка, медиатека не изменена, событие удаления не создаётся.
- Никакого удаления по команде из URL scheme, сервера или фонового процесса.

## После работы

1. Запустить доступные проверки (см. `docs/TESTING.md`): как минимум валидность `project.yml`, `xcodegen generate` (если установлен), сборку (локально, если есть Xcode, иначе — сообщить, что проверка будет в CI), ручной регрессионный чек-лист для затронутых функций.
2. Посмотреть `git diff` и убедиться, что нет случайных изменений, секретов и логирования чувствительных данных.
3. Обновить `docs/TASKS.md`: статус задачи, отмеченные acceptance criteria, заметки.
4. Если принято новое решение — добавить запись в `docs/DECISIONS.md`.
5. Дать отчёт:
   - изменённые/созданные файлы;
   - что сделано и какие решения приняты;
   - какие проверки выполнены и их результат (и какие **не** выполнены и почему);
   - риски и открытые вопросы.

## Проект

- Генерация проекта: XcodeGen (`project.yml`), `*.xcodeproj` не коммитится.
- CI: `.github/workflows/build-ios.yml` — unsigned-сборка `KatanaConnector.ipa` (artifact `katana-connector-unsigned-ipa`).
- Структура: `Sources/App`, `Sources/Core` (модели/парсеры/wire — только Foundation; Security — только Keychain; Combine — только координаторы — D-024), `Sources/Features/<Feature>`, `Sources/Shared` (только реально общее), `Tests/KatanaConnectorTests`. Без локальных SPM-пакетов и пустых заготовок (D-013, D-018).
- Wire values моделей (snake_case) после релиза не меняются; любое изменение — только вместе с тестами и записью в `DECISIONS.md`.
- Минимальная iOS: 16.0. Язык: Swift 5, SwiftUI. Только фреймворки Apple.
- Язык UI и документации — русский; идентификаторы в коде и API — английский.
